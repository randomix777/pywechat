## 2. 微信输入草稿保护

### 现有发送函数做了什么

查了 `Messages.send_messages_to_friend()`（`WeChatAuto.py:3371`），它做三件事，
**每一件都破坏用户正在输入的内容**：

| 它做的 | 后果 |
| --- | --- |
| `edit_area.set_text('')` | **清空草稿**（`GlobalConfig._clear` 默认就是 `True`） |
| `SystemSettings.copy_text_to_clipboard(message)` | **覆盖用户剪贴板** |
| `edit_area.click_input()` + ctrl+v | **抢键盘焦点** |

### 本轮的处理

**真实发送入口默认关闭**，模拟验证保留。

`src/pyweixin/wechat_send.py` 做**只读**检查：输入框当前有没有文字、前台会话是不是
目标会话、剪贴板/窗口状态能不能确认、账号是否一致。任何一项不能确认就
`hold` —— 留在队列里，不冒险发。

**不采用**「先保存草稿 → 发送 → 还原」：用户在保存和还原之间随时可能在打字，
还原回去的可能是错的内容。这种做法把明确的问题变成隐蔽的问题。

发送前**再核对一次**目标：从检查到真正发送之间商户可能已经切了会话或开始打字
（`test_merchant_typing_mid_check_is_noticed`）。

`real_sending_available()` 默认 **False**。在装有真实微信的机器上完成一次实测并
记录结果后，才可以调 `mark_real_sending_verified(True)`。首页会一直显示
「未发送原因：真实发送尚未在真机验证，目前只整理不发送」。

**未验证**：真实微信上的草稿检测、剪贴板保护、焦点行为 —— **一项都没有实测**。

## 3. 短消息合并（已接入真实路径）

`src/pyweixin/merging.py`，不是只加配置：

- **分组键** `(账号, 会话, 发送者, 话题)`。不同人不合并；有引用时按引用分话题。
- **两条时间线**：静默窗口 + 最大等待，都可调，默认 45/90 秒。
  **这两个默认值只是起点，不是「适合商户」的结论** —— 没有真实商户数据支撑。
- **持久化**：`merge_groups` / `merge_membership`，正文一起存，
  重启后缓冲区仍在。
- **不重复解析/计费/记单/发送**：原始消息被标记后，`OrderPipeline.process()`
  直接跳过；`Wizard._pending_message_ids()` 过滤掉它们，只留代表消息。
- **证据映射**：`evidence_map()` 给出代表消息 → 全部原始消息。
- **迟到**：标 `late_count`，不塞回已关闭的批次。
- **重复**：按 `event_id` 去重。
- **历史导入不合并**（逐条保留因果），合并只用于实时路径。

**已验证**（自动化）：同发送者合并、不同人不合并、不同群不合并、引用分话题、
重复投递忽略、静默窗口、最大等待（连发 20 条也会到期）、重启恢复、
迟到标记、只有代表消息被解析、证据映射。

**未验证**：真实商户的窗口长度是否合适、真实短消息的到达节奏。

## 4. 首页统计与交互

| 指标 | 口径 |
| --- | --- |
| 有效订单 | 当前未被替代、未取消的版本；**不含改量前的旧版本** |
| 需要处理 | 待核对 + 取消待核对（**自动记单不算待办**） |
| 已自动记单 | 观察值，不需要逐单确认 |
| 客户未回复确认 | 观察值，**不作为默认待办** |
| 备货汇总 | 只统计有效订单版本 |
| 待核对付款 | 客户声称已付款；**不等于已到账** |
| 发送异常 | 没发出去的 + 结果无法确认的 |

口径全部写在 `METRIC_DEFINITIONS` 里，**界面上直接显示**，并标出时间范围
（默认最近 1 天内更新的订单，可配）。

**已验证**：改一次量后备货不会变成 2+3=5 箱（被替代版本被排除）；
自动记单不进待办；统计范围之外的不计；每个指标都有成文定义。

## 5. 本轮发现并修复的缺陷

| # | 缺陷 | 影响 | 修复 |
| --- | --- | --- | --- |
| **1** | **微信导出的 `消息类型` 是中文（`文本`），解析器只认 `text`** | **每一条真实文字消息都被当成「不支持的媒体」丢进人工核对，永远不自动记单。** 上一轮「生成 22 单」其实是 22 张空卡片 | `normalize_message_kind()` 在入库关口归一化中英文类型 |
| 2 | 会话列表 `tree.selection()` 返回字符串 id，代码用它做列表下标 | **商户勾选会话点「下一步」直接崩溃** | 用 `iid=str(index)` 并转回 int |
| 3 | 413 的 drain 只限大小不限时间 | 声明 50MB 却不发数据的客户端可长期占用工作线程 | 加 `DRAIN_TIMEOUT_SECONDS=5.0` + socket 超时 |
| 4 | 恢复发送时 `release_held()` 一次性放行全部 | 暂存 20 分钟的回执可能已指向被替代的订单版本 | `held_commands()` + 逐条重新核对版本/会话/模式 |
| 5 | `SendCheck(draft_length=…)` 传了不存在的关键字 | 草稿非空时守卫直接抛 TypeError | 改用 `detail` |
| 6 | `MessageMerger.flush()` 拿 `MergeGroup` 当 `MergeKey` 用 | 到期结算直接 AttributeError | 分派参数类型 |
| 7 | `mark_late()` 只改库不改内存 | 结算时 `late_count` 恒为 0 | 内存与库同时更新 |
| 8 | 合并组重启后无法恢复正文 | 重启会把订单拆成两笔 | 正文随 membership 一起持久化 |
| 9 | 缺失/过期回执被报成「生成订单」 | 商户以为记单成功 | 统计区分「已记单」与「待核对卡片」 |
| 10 | 首页「客户未确认」当默认待办 | 自动化成果又变回人工清单 | 移出主计数，降为观察值 |

缺陷 1、2 是**只有真正点按钮、真正喂真实形状数据**才会暴露的 —— 逐页渲染截图
和直接调用内部函数的测试都发现不了。

## 6. 恢复与限流复核

| 检查项 | 结论 | 验证 |
| --- | --- | --- |
| 明确未提交的失败可有限重试 | 是，仅 `network_error`/`rate_limited`，≤2 次 | `test_network_error_before_submission_is_retried` |
| 可能已提交的断连不重跑 | 是，`outcome_unknown` / `timeout` 不重试 | `test_unknown_outcome_is_not_re_executed`、`test_timeout_does_not_retry_either` |
| 不重复扣额度 | 结果未知时 `cost_units=0` | 同上 |
| 恢复发送逐条重核 | 版本/会话/模式任一不符继续暂缓 | `test_resuming_releases_only_still_valid_receipts` 等 3 项 |
| 413 drain 时间封顶 | 5 秒，实测声明 50MB 的空请求 **1.0 秒**返回 413 | `test_slow_body_does_not_hang_the_handler` |
| 413 drain 大小封顶 | 8 MB | `test_drain_has_a_size_limit` |
| 后台线程不叠加 | 单线程、幂等停止、无残留 | 上一轮 `ThreadHygieneTests` |
